# 太阳IP客户端：设计审阅报告

- 审阅日期：2026-10-10，Asia/Hong_Kong。
- 审阅对象：[太阳IP客户端：需求与架构设计](../specs/2026-10-10-sunipip-client-design.md)（下称“主设计”，引用时写作“主设计 §x”）。
- 审阅视角：产品/项目管理（范围、优先级、依赖、交付风险）与工程实现（架构、安全、可测试性、可运维性）。
- 配套文档：[补充设计](../specs/2026-10-10-sunipip-client-design-addendum.md)（针对缺失项给出具体设计）、[实施计划](../plans/2026-10-10-sunipip-client-implementation-plan.md)。
- 本文是审阅意见与建议，不改变主设计已确认的内容；第 7 节的待决策事项确认后，再把结论合并进主设计。

## 0. 结论摘要

主设计在**业务边界**上很扎实：逐资源判断中转资格、绝不回退到原始静态 IP、出口绑定同一资源、断线后不自动直连、明确区分“网站暂时不可达”和“权益到期”，并如实写明哪些事项尚未验证。这些原则应全部保留。

主要问题集中在三方面：

1. **范围过宽**。首版同时铺开三条产品线（Win10/11、安卓、Win7）、两个内核、十余种协议、自建 DNS 解析器和分流规则预留。现阶段只交付 SOCKS5，大部分预留不产生用户价值，却显著增加实现与测试量。共识别 **9 项多余或可简化设计**（第 3 节）。
2. **关键工程设计缺失**。状态模型、字段级资格规则、Windows 特权服务与防火墙规则生命周期、业务 DNS、App 自身请求的路径、错误码、版本治理和发布工程都没有设计，按现状直接开发会边做边定、反复返工。共识别 **30 项缺失**，其中 P0 级 10 项（第 4 节）。
3. **服务端依赖没有落实**。客户端计划按 GPL-3.0 开源，任何人都能删掉客户端里的资格判断；“仅开通中转的资源可连接”只有在中转服务端拒绝过期或未授权凭据时才真正成立。这一项必须在开发前与后端确认（第 6 节）。

**建议**：首个正式版（GA）收窄为 “Windows 10/11 x64 + Android 8.0+，仅 SOCKS5，sing-box 单内核，全局默认出口”；Win7 兼容版改为 GA 后的决策门；正式开发前先用 3 周做技术验证（Phase 0），验证结论写成架构决策记录（ADR）后再进入编码。详见[实施计划](../plans/2026-10-10-sunipip-client-implementation-plan.md)。

## 1. 审阅方法与分级

| 分级 | 含义 |
| --- | --- |
| P0 | 不解决就无法开始实现，或会导致大面积返工、安全或资金风险 |
| P1 | 公开测试（Beta）前必须解决 |
| P2 | 正式版（GA）前或之后解决 |

多余设计的处置分三类：**删除**（首版及近期都不需要）、**推迟**（保留方向，移出首版）、**简化**（保留能力，降低实现复杂度）。

## 2. 应保留的设计

以下内容判断正确，建议原样保留，后续修订不要削弱：

- 数据源适配层隔离网页原始字段（主设计 §3、§4）。正式 API 上线时只需新增适配器。
- 字段缺失或解析失败显示为“同步异常”，不当作“没有 IP”（主设计 §4.3）。
- 逐资源判断“资源—订阅—中转规则”，不因为账号买过一条中转就解锁全部资源（主设计 §5）。
- 客户端不继承网页“回退到资源原始地址”的兜底路径（主设计 §4.2）。
- 网站临时不可达不中断已有连接，到期或撤销才停止，且不延长权益（主设计 §5）。
- 全局接管下任何故障都不自动转为直连，自动停止不等于用户同意直连（主设计 §6.2）。
- 安卓区分 App 级保护和系统级保护，无法核实的状态不显示为“已启用”（主设计 §7）。
- 显示“已连接”之前必须经所选线路实际验证出口（主设计 §10）。
- 诊断信息脱敏，不自动上传日志（主设计 §10）。
- 如实写明验证边界：构建成功不等于运行通过，未测项不写成已支持（主设计 §13）。

## 3. 多余设计与可简化项

| 编号 | 原设计位置 | 问题 | 建议处置 |
| --- | --- | --- | --- |
| R-01 | §2 Win7 兼容版 | 与主力版同期推进第二套界面、内核、系统接管、更新通道和测试矩阵，工作量约为 Windows 主力版的 60%–80% | **推迟**：设为 GA 后决策门；首版缩小范围；先评估共享原生层的路线 |
| R-02 | §9.1 主力版预留 Xray 适配 | sing-box 已覆盖全部目标协议，主力版再接 Xray 只增加测试组合 | **删除**：主力版只接 sing-box；内核适配接口保留，但只有一个实现 |
| R-03 | §9.1 协议清单与协议迁移 | 现在只交付 SOCKS5，却要对 VLESS、Trojan、Hysteria2、TUIC、AnyTLS 等分别建模，还要支持新旧配置并存 | **推迟**：首版只实现 SOCKS5；模型留出协议类型字段和版本号，等服务端确定新协议后再按需增加 |
| R-04 | §3、§8 自建入口解析器 | 多上游竞速、TTL 缓存、响应校验、DoH、DoH 自举、TLS/SNI 路径都要自己写，大部分与内核的 DNS 和出站绑定能力重叠；SOCKS5 本身也不涉及 TLS | **简化**：首版只做最小解析器（多上游并发、超时、TTL 缓存、错误分类、失败后重新解析），或直接使用内核能力，由 Spike S8 决定；DoH 与 TLS/SNI 推迟 |
| R-05 | §3、§9.2 独立路由策略模块 | 首版只有“全部公网走所选出口”这一种策略，却预留了域名、IP 段、优先级、动作、配置版本和按应用分流 | **简化**：首版只保留两个参数，即“默认动作 = 代理”和“允许局域网访问（开/关）”，不建规则模型；规则编辑器和按应用分流整体推迟 |
| R-06 | §4.1 完整分页同步 | 为了一次性拉全量，需要处理遍历分页、去重和同步期间总数变化；资源多的账号还会放大请求量 | **简化**：列表浏览沿用网页的服务端分页和筛选，只按 ID 去重；连接或切换前只刷新所选资源（依赖后端依赖 B-05） |
| R-07 | §4.1 账号级订阅配置 | `/subscriptions/config` 返回带令牌的订阅链接，首版用不到，反而多一个敏感数据面 | **删除**（首版）：多协议阶段再评估 |
| R-08 | §11 更新匹配与回退 | 按“内核能力”匹配更新包，客户端还要保存上一版本以便回退，复杂度高；安卓本身也做不到直接降级 | **简化**：更新只按平台、架构、通道、最低系统版本匹配；回退统一采用“把上一稳定版代码以更高版本号重新发布”，配置结构只增不改 |
| R-09 | §2、§3 macOS / iOS 预留 | “预留 Swift / Network Extension 适配”容易被理解成需要投入 | **简化**：只在架构上保留平台适配边界，本期零投入（不建工程、不申请开发者账号） |

### R-01 Win7 兼容版

- Win7 已于 2020 年停止支持，扩展安全更新也已于 2023 年结束；Go 自 1.21 起官方工具链不再支持 Win7，sing-box 和 Xray 的 Win7 构建都依赖打过补丁的工具链。这条线的长期维护成本只会越来越高。
- 主设计已确认要支持 Win7，本审阅不推翻这一结论，只建议调整时机和首版范围：
  1. **时机**：主力版 GA 后 4 周召开决策会，以“活跃 Windows 用户中 Win7 的占比”作为启动门槛（建议 ≥ 5%；数据来自客服统计和用户调研）。
  2. **首版范围**：Win7 版首版只做登录、资源和系统代理连接，不做 TUN 和断线保护。Win7 现有用户本来就在用 v2rayN 的系统代理模式。
  3. **路线评估**：先验证“用 go-win7 工具链编译主力版同一套 Go 原生服务（内嵌 sing-box）”是否可行。如果可行，Win7 版只需重写 WPF 界面，内核、配置生成和保护逻辑都能共用，Xray 第二内核也可以省掉。这只是待验证的假设，不是结论。
- 在 Win7 版发布前，为 Win7 用户提供官方的 v2rayN 配置指南，作为过渡。

### R-04 入口解析器

sing-box 的出站拨号字段已经支持 `domain_resolver`，路由支持 `auto_detect_interface`（Windows 下把出站连接绑定到物理网口，避免流量绕回自己的 TUN），安卓上通过平台接口调用 `protect`。另外，sing-box 1.12 起已弃用部分 DNS 相关字段，并计划在 1.14 移除，说明内核配置格式还在变化。因此：

- 入口解析的**策略**（候选服务器、超时、错误分类）可以留在 App；**执行**应尽量交给内核，或放在能绑定物理网络的原生层，不要用 Dart 实现一个通用解析器。
- 具体做法由 Phase 0 的 Spike S8 决定；DoH 和“TLS 协议下用原域名做 SNI”等内容推迟到引入 TLS 类协议时再做。

### 4.2 P0 缺失项说明

**G-01 服务端强制校验。** 主设计 §5 已经写明“服务端认证才是最终边界”，但把它列为“尚未检查”。客户端开源后，任何人都可以编译一个不做资格判断的版本。即使不开源，资源本身也带着 `auth_username`/`auth_password`，用户可以直接填进 v2rayN。因此客户端里的资格判断只是**产品体验**（告诉用户为什么不能连、该去哪里开通），不是安全措施。必须在开发前确认中转服务端会在到期、停用、撤销后拒绝认证，并确认生效有多快。

**G-02 登录流程。** 主设计 §4.1 只列了 `POST /auth/login-sms`，没有“发送短信验证码”的接口；发送验证码通常要先通过图形或滑块验证。`403 VERIFICATION_REQUIRED` 可能是人机验证，也可能是实名或新设备验证，客户端需要提前知道该弹什么界面。如果验证依赖网页脚本（例如第三方验证码组件），原生 App 就要内嵌网页来完成登录，这会直接影响界面设计和工作量。另外还要确认：令牌多久过期、能否刷新、网页登录是否会把 App 挤下线。

**G-03 账号级门槛。** 主设计 §5 的资格表只看资源。但 `/auth/me` 返回“账户级状态”，`customer.forward_certified` 从字面看像是“中转认证已通过”。主设计只说它“不能单独证明每条资源已购买中转”，没有回答它是不是**必要条件**。如果是，账号未认证时所有资源都应显示“账号受限”，而不是逐条显示“可连接”。

**G-04 字段级规则与一致性。** 主设计没有给出 `active_subscription.status`、`forward_rule.status` 的取值全集，也没有说 `expires_at` 的格式和时区，“有效”只是概念。主力版（Dart）与 Win7 版（C#）各自实现资格判断，没有共享测试向量，两边判断结果迟早会不一致。补充设计 §5 给出了有序判定表和共享测试向量格式。

**G-05 状态模型。** 主设计 §10 的连接状态把“同步中”（数据状态）、“受限”（资格状态）和“连接中/重连中”（连接生命周期）放进同一个枚举，会出现“同步中但已连接”这类无法表达的组合。另外没有定义状态迁移、各阶段超时和重连退避。补充设计 §3 把状态拆成会话、资格、连接、保护四个互相独立的维度。

**G-06 Windows 特权服务。** TUN 和防火墙规则需要管理员权限，主设计只写了“受控后台组件”。以 SYSTEM 身份运行的服务如果接受任意内核配置，就可能被本机其他程序利用来提权，因为内核配置里可以写日志路径、缓存文件路径，等于获得以 SYSTEM 身份任意写文件的能力。必须明确：服务只接受结构化参数，内核配置由服务自己生成；命名管道要设置访问控制，并校验调用方的签名和路径。另外，系统代理是**按用户**设置的，必须由用户会话内的界面进程来设置，不能放在服务里。

**G-07 防火墙规则生命周期。** 断线保护依赖 WFP 规则。规则如果随进程消失，进程一崩溃就会泄漏；如果写成永久规则，一旦出 bug 或卸载不干净，用户就会彻底断网。主设计 §6.2 提到了“记录可恢复状态”和“残留检测”，但没有写崩溃、重启、升级、卸载各种情况下规则怎么处理，也没有设计 App 打不开时的兜底手段。补充设计 §8 给出了规则的会话和持久化策略，以及独立的“网络修复工具”。

**G-08 业务 DNS。** 主设计 §8 写的是“客户业务的域名解析通过所选中转线路处理”，但没有说怎么处理。对这类用户（需要固定出口的账号运营场景），最重要的是：解析在出口侧完成（CDN 返回的节点与出口 IP 所在地一致），而且不能有明文 DNS 从物理网口漏出去。在 TUN 模式下应该采用“域名嗅探 / FakeIP + 以域名形式交给 SOCKS5 远端解析”；如果中转不支持 UDP，也绝不能把 DNS 改为从本地直连发出。

**G-09 控制面路径。** 登录、同步、远程配置、更新下载、出口检测分别从哪里出去？TUN 模式下 App 自己的请求会被 TUN 捕获；保护阻断时还需要放行；WFP 只能按程序或 IP 过滤，无法按域名过滤。如果登录要内嵌网页（WebView2 运行在独立进程），按程序放行也会失效。补充设计 §6 用一张流量路径矩阵把这些情况逐一写清。

**G-10 错误码。** 三端共用一套错误码，客服才能凭用户截图或诊断包里的编码直接定位原因。补充设计 §14 给出了编码规则和首批错误码。

## 5. 矛盾、歧义与表述问题

| 编号 | 位置 | 问题 | 建议 |
| --- | --- | --- | --- |
| C-01 | §10 | 连接状态把数据同步、资格和连接生命周期混在一起 | 拆成四个独立的状态维度（补充设计 §3） |
| C-02 | §6.1 | 连接顺序是“先设系统代理，再做实际验证”。验证失败时用户流量已经走了未经验证的代理，还要回滚 | 改为：内核启动 → 经本地入口验证出口 → 成功后再接管系统代理 |
| C-03 | §5 表格 | 到期自动停止时，TUN 模式有保护；系统代理模式下是恢复直连还是保持代理失效，没有定义 | 见 D-08：保持系统代理指向已停止的本地端口（对遵循代理的程序等于阻断），由用户选择“恢复直连” |
| C-04 | §1、§5 | 保护阻断时，“查看中转服务”“联系客服”的网页链接同样打不开 | 客服联系方式（文字或二维码）随远程配置缓存在本地，断网时也能查看 |
| C-05 | §4.2 | 入口来源的第 4 级 `original_connect_host` 是否属于中转入口没有确认，可能与“不得回退原始地址”的原则冲突 | 列为后端依赖 B-03；确认之前，第 4 级入口视为“配置异常” |
| C-06 | §6.2、§8 | “只放行受约束的控制请求”，但控制面目标是域名，WFP 无法按域名过滤 | 改为按程序路径放行（界面进程、服务进程），并限制协议和端口（补充设计 §8） |
| C-07 | §12 | 验收标准都是定性描述，没有阈值和测试方法 | 补充量化门禁（实施计划 §13） |
| C-08 | §11 | GPL 的原因（安卓链接 libbox，Windows 服务内嵌 sing-box）没有写明；Win7 版（WPF + Xray，Xray 为 MPL-2.0）的许可证没有定义 | 写明原因；Win7 版许可证在 R-01 决策门一并决定 |
| C-09 | §2、§9.1 | “Win7 用 Xray”和“主力版预留 Xray”是两回事，但读起来容易混淆 | 执行 R-02 后，Xray 只与 Win7 版相关 |
| C-10 | §5 | “恢复同一逻辑会话”没有定义：App 重启、系统重启之后还算不算 | 定义为“用户没有主动断开，且保护或连接意图仍然记录在本地”；跨 App 和系统重启都算（补充设计 §3.6） |
| C-11 | §7 | “接管全部应用”与“控制面直连”之间的关系没有说明，App 自身要不要排除在 VPN 外 | 由 Spike S7 决定：App 自身排除在 VPN 外，或使用 `protect` 绑定底层网络（补充设计 §9） |
| C-12 | §6.1 | “启用 TUN 时按需获取系统权限”与“由受控后台组件处理高权限操作”不一致：常驻的特权服务在安装时已经取得权限，运行时不需要再次申请 | 改为安装时一次授权；“取消授权”这一失败场景改为“服务未运行或版本不匹配”（补充设计 §2.2） |

| D-05 | 资源列表的获取方式 | 服务端分页筛选 + 连接前只刷新单条资源 | 若改为全量同步，约 +1 人周，并增加限流风险 |

| D-07 | 出口检测失败时显示什么 | 中转握手和认证成功、只是检测服务失败时，显示“已连接·出口未核实”并给出警告；中转认证失败则显示“失败” | 影响状态机与文案 |
| D-08 | 系统代理模式下到期自动停止后，系统代理怎么处理 | 保持指向已停止的本地端口（遵循代理的程序会断网），提供“恢复直连”按钮；退出程序时恢复原设置 | 影响 C-03 |
