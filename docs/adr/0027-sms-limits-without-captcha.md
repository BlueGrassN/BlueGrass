# ADR 0027：短信登录仅使用限流，不使用人机验证

- 状态：已接受，短信接口与客户端待实现。
- 决策日期：2026-10-11，Asia/Hong_Kong。
- 对应事项：全项目复核 C02；细化 D-16、D-26 的短信流程。
- 确认依据：用户选择 C；不使用图形、滑块等人机验证，仅限制短信发送频率、发送数量和验证码错误次数。

## 决定

1. 客户端短信登录不接入图形验证码、滑块或其他人机挑战，正常请求和超过限额的请求都不进入人机验证分支。
2. 独立 Go API 执行发码间隔、发送次数配额和验证码错误尝试次数限制。达到限制后拒绝请求，并返回可识别的限流/验证码失效结果及适用的等待信息；客户端显示原因和重试时间。
3. 服务端限制是实际执行依据，客户端按钮倒计时只提供交互反馈，不能作为唯一的限流措施。并发请求、多实例以及更换设备不能绕过同一手机号适用的限制；来源 IP 等入口预算与供应商总额度在具体契约中一并落实。
4. 验证码仍须有明确有效期与一次性消费规则；错误次数用尽后的失效、重新发送和等待行为在参数契约中规定，不通过弹出人机验证解除限制。
5. 沿用 D-26 的现有短信供应商、签名和模板，由独立 Go API 负责发送、校验及会话签发。短信端点、具体限额和验证码参数尚未实现或确认。
6. 取消客户端短信登录所需的验证网页、第三方验证票据、票据 IP 绑定及其专用网络路径。短信发送与登录请求使用既定 API 控制通道，保护状态下仍须验证该通道可达。

## 与既有设计的关系

- D-16 的密码与短信两种登录继续保留；其中原“必要的人机验证”范围按本决定移除。
- D-26 中待确认的人机验证触发/票据条目由本决定替代，不再列为短信验收依赖。
- 注册、找回密码等跳转官网的流程不因本决定修改官网自身的验证要求；本决定只规定客户端独立登录流程。
- 原网页方案及旧审计中的验证票据/IP 绑定记录作为历史依据保留，不再作为当前短信实现或发布门禁。
- 当前密码接口和已发布的 API 行为没有因本设计记录发生变化。

## 尚需定稿

2026-10-11，用户决定稍后讨论参数来源与具体数值。尚未选择沿用官网参数或另行制定，不采用任何一组默认值；D-26 的短信服务配置复用和本 ADR 的不使用人机验证决定继续有效。

验证码格式与有效期、重发间隔、各时间窗口发送上限、错误次数及重置规则、手机号和 IP 预算、发送超时/重复请求的计数、跨实例计数存储和错误响应。具体数值在后续确认，不把本次 C 选项视为已批准某组默认参数。

## 验证要求

- 发码、登录失败、达到发送或校验限额时，客户端没有图形/滑块、验证网页或第三方验证票据请求。
- 限流和错误次数控制由服务端执行；修改客户端倒计时、并发提交、跨实例请求不能绕过已确定的配额。
- 正确展示等待时间、发送失败、验证码错误/过期及次数用尽；发送被拒绝不伪装成成功。
- 一次性消费、重发和网络超时恢复按定稿契约执行；密码与短信完整登录均在 Windows/Android 及保护状态下验收。
