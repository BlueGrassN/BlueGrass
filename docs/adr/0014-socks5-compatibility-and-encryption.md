# ADR 0014：保留 SOCKS5 兼容并逐步迁移加密入口

- 状态：已接受。
- 决策日期：2026-10-10，Asia/Hong_Kong。
- 对应事项：设计审阅报告 D-14。
- 确认依据：用户选择 A，保留现有 SOCKS5 线路，说明传输边界，后续配合服务端迁移加密协议。

## 决定

1. 首版继续支持现有具备有效中转资格的 SOCKS5 资源，不以全部存量线路先完成加密迁移作为客户端发布前提。
2. 帮助文档和资源详情如实说明客户端采用的协议与传输保护。用户名/密码认证的 SOCKS5 自身不加密该认证信息；链路是否另有加密保护应依据实际配置和验证结果，不凭推测宣称安全。
3. D-03 已确认的多协议能力继续纳入首版实现与测试。服务端逐步提供对应加密入口和参数后，客户端通过版本化连接配置接入；不把客户端支持清单等同于服务端已经部署的清单。
4. 迁移必须保持可靠的资源和住宅出口对应关系，重新校验资格、协议能力、认证参数及实际出口。不能按入口地址或名称猜测为同一资源。
5. TLS 类配置保留原始域名、SNI 和证书验证；加密认证或握手失败不能自动降级为明文 SOCKS5，也不能切换到其他住宅资源。
6. 兼容配置仅在服务端仍授权、参数完整且通过资格与出口验证时使用；配置被撤销、到期或明确停用后，不能借旧协议继续连接。

[D-24](0024-one-protocol-per-resource.md) 明确每个资源只提供一种协议。上述迁移按服务端更新该资源的当前协议配置理解，不增加同资源多协议候选或客户端协议选择器。

## 展示与验证边界

- 协议、传输和安全参数分开建模；加密状态依据 S12 验证过的具体组合，不能仅从协议名称推断。
- TUN/VPN 的流量接管与客户端到中转入口的传输加密是不同能力，不把“全局接管已开启”显示成“中转传输已加密”。
- 产品说明区分代理认证信息和业务载荷的保护，不将 SOCKS5 描述成所有 HTTPS 业务正文均为明文。
- 未知的外层保护不宣称已验证；诊断只报告能确认的协议配置与检测结果，不输出真实认证信息。

## 验证要求

S3/S12 分别记录当前服务端实际协议、可提供的测试配置和迁移安排。验证既有 SOCKS5 兼容、同资源新配置映射、证书或认证失败、旧配置撤销，以及加密失败时没有隐式降级。真实服务端未提供的协议用受控线路验证客户端能力，并明确验证范围。

## 协议依据

[RFC 1929 §3](https://www.rfc-editor.org/rfc/rfc1929.html#section-3)说明 SOCKS5 用户名/密码子协商会以明文携带密码；[RFC 1928 §4](https://www.rfc-editor.org/rfc/rfc1928.html#section-4)定义连接请求中的目标地址。是否有额外加密封装需要依据实际链路与配置核实。本决策不表示已完成现有线路抓包或服务端加密部署验证。
