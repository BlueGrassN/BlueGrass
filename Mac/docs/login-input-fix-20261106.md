# Mac 登录框输入修复 — 2026-11-06

用户反馈：其他按钮能够点击，账号和密码框没有光标、无法输入，页面没有错误提示。

## 已复现的问题

共享登录页把输入框的启用条件写成 `!c.busy && c.canLogin`。生产控制器在启动时先读取设备记录并检查原有网络保护；这一阶段 `recoveryRequired` 为真、`canLogin` 为假，但 `message` 可以仍为空。输入框因此被禁用，点击无法获得焦点。

新增回归使用真实 `AppController`，暂停其设备记录读取，分别以 macOS 和 Windows 平台策略运行。测试通过鼠标点击获取焦点，再模拟键盘输入，而不是强制调用输入框聚焦。修复前，两种平台的启动等待测试和恢复未确认测试均以“期望有焦点，实际无焦点”失败。

## 修改

仅将账号和密码框的启用条件改为 `!c.busy`，允许启动、恢复检查期间先填写凭据。登录按钮、提交处理器和控制器仍检查初始化、网络保护、忙碌及会话清理状态；输入和按回车不能绕过这些检查。正在提交登录时仍禁止编辑，密码仍保持遮蔽。

Mac 和 Windows 继续使用同一登录页，没有修改 AppKit 窗口、原生焦点、Keychain 或 TUN 行为。Mac 工作流加入 `protected_login_ui_test.dart`，后续构建会运行本次回归。

## 验证

- 修复前：三个鼠标焦点回归失败；修复后相关登录、Mac 平台与 TUN 保护测试 31 项通过。
- Mac 启动器 3 项测试通过；共享应用和 Mac 启动器静态分析无问题。
- 完整共享应用测试 440 项全部通过。
- Mac 工作流通过 actionlint（沿用旧版检查器对已验证 Intel runner 标签的例外）。

本地验证运行在 Windows；macOS 平台策略测试不等于 Cocoa 原生键盘事件验收，也不能证明用户机器上的所有可能原因已排除。请使用下一次包含此修复的 Mac 包复测：首次启动即点击账号和密码，检查光标、键盘输入、密码遮蔽；检查完成前不得提交，完成后应可正常登录。已有旧测试包不包含本次改动。

GitHub 的 Mac 构建会运行上述焦点和提交保护回归；实际用户设备的键盘输入与登录仍需使用包含此修复的新包确认。
